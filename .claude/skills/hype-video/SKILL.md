# ハイプ動画の設計と制作（AviUtl）

## このスキルの前提

**動画は再生できない。音も聞けない。** URL を渡されても中身は見えない。
代わりに、mp4 のファイルさえ手元にあれば **数値とコマ画像に落として読む**ことができる。
これが「参考動画っぽく編集する」ための唯一の確実な道筋になる。

やることは3つ。順番に意味がある。

1. **参考動画を実測する** — 印象論ではなく数字で仕様を出す
2. **撮影を設計する** — 編集で盛れる量は素材で決まる。撮り直しはきかない
3. **AviUtl で組む** — 実測した数値をそのまま設定に落とす

参考動画がない場合は 2 から始めればよい。

---

## 1. 参考動画を実測する

### 動画ファイルを手に入れる

ユーザーが mp4 を添付できるならそれが一番早い。URL しか無い場合は、
**画面録画かスクリーンショットを送ってもらう**よう頼む。
YouTube などからのダウンロードは規約に反するので勧めない。

コマ画像（スクショ）だけでも、色味・テロップ・構図は読める。
動画ファイルがあれば、それに加えてカットの速さと BPM まで読める。

### 解析を回す

```bash
pip install av librosa imageio-ffmpeg numpy pillow
python scripts/analyze_reference.py 参考.mp4 -o out/
```

`scripts/analyze_reference.py` が、1回のデコードで次をまとめて出す。

- カットの切り替わり位置と、長さの分布
- 音声の BPM、最初のビート、音が落ちる区間
- カットがビートグリッドに乗っている割合（**偶然の期待値つき**）
- 黒レベル・白レベル・平均輝度・彩度・色かぶり
- 上下左右の黒帯と画面比
- カットごとの代表コマを並べた **コンタクトシート PNG**

環境に ffmpeg が無いことがある。Playwright 同梱の ffmpeg は
機能を削った版で mp4 を読めないので、`imageio-ffmpeg` を入れて使うこと（スクリプトが自動で探す）。

### 出力の読み方

**コンタクトシートは必ず Read ツールで開いて実際に見ること。**
数値だけでは、テロップの字体・位置、構図、被写体の混ぜ方が分からない。
ここを飛ばすと「それっぽい数字を並べただけ」の解析になる。

音ハメの判定には注意がいる。細かいグリッドほど偶然当たるので、
**実測値と偶然の期待値を必ず比べる**。スクリプトはこれを併記する。
実測が期待値の1.6倍を超えて初めて「音ハメしている」と言える。

多くのプロのトレーラーは、実は厳密な音ハメをしていない。
カットは動きの見せ場で切って、曲の展開（イントロ／サビ／ブレイク）とだけ合わせている。
**測った結果が「偶然の範囲」なら、その事実をユーザーに伝えること。**
思い込みで「音ハメしましょう」と書くと、参考動画と違うものになる。

## 2. 実測値を AviUtl の設定に落とす

解析の数字は、そのまま操作に変換できる。ここがこのスキルの中心。

| 実測項目 | 読み方 | AviUtl での操作 |
| --- | --- | --- |
| 黒レベル 0〜5/255 | 黒を潰している。硬い・現代的 | 色調補正でコントラストを上げる |
| 黒レベル 15〜25/255 | **黒を持ち上げている＝フィルム調** | 色調補正の後に、黒い単色オブジェクトを不透明度92〜95%で全面に重ねるか、コントラストを下げて明るさを少し上げる |
| 白レベル 200〜215/255 | ハイライトを抑えている | 白飛びさせない。グロー弱めで代用 |
| 平均輝度 80〜95/255 | 全体に暗い（ハイプ動画の定番） | 明るさをむしろ下げる。暗いほど文字が映える |
| 彩度 40%前後 | 意外と鮮やか。地味にしすぎない | 彩度は落としすぎない。落とすなら5〜15%まで |
| R−B が +8以上 | 暖色寄り（炎・夕方・熱） | 色調補正の色相をわずかに暖色へ |
| R−B が −8以下 | 寒色寄り（夜・緊張感） | 同じく寒色へ |
| 黒帯あり | レターボックス | 図形(四角形・黒)を上下に配置 |
| 黒帯なしで比率が16:9でない | 素材自体が横長 | 1920×1080 で再現するなら上下に黒帯。必要px数はスクリプトが計算して出す |
| カット長の中央値 | カットの基準の速さ | この長さを基準にタイムラインを割る |
| カット長の25%点が0.2秒以下 | **速いカットの塊を挟んでいる** | 全体を均等に速くするのではなく、数カットだけ連射する |
| ビート整合が偶然超え | 音ハメしている | beatgrid.html でフレーム番号を出して割る |
| ビート整合が偶然の範囲 | 動き優先で切っている | ビートに縛られず、当たる瞬間・走り出す瞬間で切る |

### カットの速さは「平均」で設計しない

ハイプ動画のリズムは、**同じ長さの繰り返しではなく緩急**でできている。
実測すると、中央値0.6秒あたりに山があり、そこに0.2秒未満の塊が2〜3割混ざる、
という分布になることが多い。設計としてはこう組む。

- 基準の長さ（中央値）でしばらく進める
- 見せ場で **0.15〜0.2秒のカットを3〜5連発**する
- そのあと **1.5〜3秒の長いカット**を1つ置いて呼吸させる

均等割りは、速くしても単調になる。緩急が「かっけえ」の正体。

## 3. 撮影を設計する

編集は素材の質を超えられない。撮る前にこれだけは伝える。

| 項目 | 設定 | 理由 |
| --- | --- | --- |
| フレームレート | 60fps。スローにするカットは120fps以上 | 30fpsで撮るとスローにできない。後から取り返せない |
| シャッタースピード | fps の約2倍（60fps→1/120） | 遅いとブレ、速いとパラパラして安っぽい |
| 時間帯 | 夕方の斜光か曇り | 昼の順光が一番かっこよく撮れない |
| 構図 | 同じ場面を寄り・引き・ローの3種 | 編集はアングルの切り替えで成立する |

撮るべきカットの一覧と、やりがちな失敗は `references/shooting.md` に書いてある。
競技や題材が変わっても、**「動きのカット」と「間を作るカット」を両方撮る**という原則は変わらない。
間のカット（手元、表情、息、道具、無人の会場）が足りないと、どれだけ速く切っても単調になる。

## 4. 編集を組み立てる

### 曲を先に決める

曲が決まらないとカットの長さも構成も決まらない。**BGM を先にタイムラインへ置く。**
そのうえで曲の展開（イントロ／Aメロ／サビ／ブレイク）の秒数をメモしてから映像を並べる。
映像から並べると必ず破綻する。

解析スクリプトが出す「音が落ちる区間」は、そのままブレイクの位置として使える。

### 構成の型

| 区間 | 長さ | 内容 |
| --- | --- | --- |
| 導入 | 5〜10秒 | 環境音だけ。寄りのカット。全部スロー |
| 開始の一撃 | 1秒 | 曲の1拍目でタイトル、または一番強い当たり |
| 高速パート | 30〜40秒 | 基準の速さ＋連射＋長回しの緩急 |
| ブレイク | 3〜5秒 | 音を落として1カットだけスロー。落差が効く |
| サビ | 30〜40秒 | 一番いい場面 |
| 締め | 10秒 | 全体の画 → チーム名・年度・情報 |

全体 **1分30秒〜2分30秒**。2分を超えたら削ることを検討する。

### スローモーション

撮影 fps とプロジェクト fps の関係を外すとカクつく。

- 120fps 素材 → 60fps プロジェクトで再生速度50% … なめらか（推奨）
- 240fps 素材 → 60fps プロジェクトで25% … かなり遅くできる
- 60fps 素材 → 60fps プロジェクトで50% … 同じコマが2回出て少しカクつく
- 30fps 素材 → スローにできない

映像オブジェクトの「再生速度」を下げ、短くなった分だけ右端を伸ばす。
途中から遅くしたい場合は、その位置で分割して後ろ側だけ下げる。

## 5. AviUtl スクリプト

`assets/` に5つのアニメーション効果を用意してある。`exedit.auf` と同じ階層の
`script` フォルダにコピーして AviUtl を再起動すると、
オブジェクト設定の「＋」→「アニメーション効果」から選べるようになる。

| ファイル | 効果 | 使いどころ |
| --- | --- | --- |
| `beat_punch.anm` | BPM を入れると拍ごとに瞬間ズーム | カットを割らない長回しにリズムを足す |
| `impact_shake.anm` | 先頭で強く揺れて収まる | ぶつかる・決まる瞬間のカットの頭 |
| `telop_kick.anm` | 行き過ぎてから戻る（オーバーシュート） | 短く出す普通のテロップ |
| `telop_drift.anm` | 数秒かけて一定速度で流す | **キャッチコピーを出しっぱなしにする** |
| `ease_push.anm` | カーブ1本で緩急を変えられる寄り・流し | 止め絵に動きを足す。溜めを作る |

`assets/beatgrid.html` はブラウザで開くだけの計算機。BPM とフレームレートから、
カットを置くフレーム番号の一覧を出す。BPM が分からない場合はタップで測れる。
**音ハメすると判断したときだけ使う。**

### イージングを外さない

同じ距離を同じ時間で動かしても、**速度の変化のさせ方**で印象が変わる。
素人っぽさが一番出るのがここ。

- **イーズアウト（速く出て、長く止まる）が基本。** 現実の物体がそう動くので自然に見える
- **イーズイン（そろそろ出て最後に加速）は溜め。** ブレイクやクライマックス直前に使う
- **等速は無機質。** キャッチコピーの流しにはむしろ合う（`telop_drift.anm` の既定が等速なのはこのため）

`ease_push.anm` の `カーブ` を +60／−60／0 で切り替えるか、
AviUtl 本体の中間点＋移動方法（加減速移動・曲線移動）を使う。
複雑な軌跡は中間点、単純な寄りはスクリプトのほうが早い。

**スローモーションにもイージングが要る。** 100%から急に25%へ落とすと段差が見える。
分割して段階的に速度を変えるのが基本だが、**各段を均等割りにするのはイージングではなく直線**。
`assets/speedramp.html` に値を入れると、カーブに沿ってサンプルした段ごとの速度と、
AviUtl でそのオブジェクトを分割するフレーム位置が出る。目安は1段あたり最低3フレーム。
それより短い区間に無理に段数を詰めると、どのカーブを選んでも差が見えなくなる。

### 一番効く文字の見せ方

短いテロップをパッパッと出すより、**キャッチコピー1つを3秒前後そのまま出し、
その下で映像を5〜10カット切り替える**ほうが強い。文字が動かず映像だけが変わるので、
言葉に重みが出る。これに `telop_drift.anm` を使う（縦150px前後をゆっくり流す）。

テロップの字体・配置の型は `references/telop.md` にまとめてある。
太字＋黒フチが常に正解ではない。暗い映像に細めの白文字を置くだけのほうが
上品に決まることが多く、実際のトレーラーはそちらが主流。

## 6. ラフカットを自動で組む

素材が数十本あると、全部見て使えるところを拾うだけで数時間かかる。
`scripts/build_roughcut.py` がそこを引き受ける。

```bash
pip install av numpy pillow imageio-ffmpeg
python scripts/build_roughcut.py --footage 素材フォルダ --music Prime.mp3 \
    --plan scripts/prime_plan.json --out roughcut.mp4 \
    --title "○○高校ラグビー部" --tagline "ここに一言。"
```

やっていること。

1. 素材を1本ずつ解析し、0.5秒ごとに動き・明るさ・輪郭の量を測る
2. 「動き × 輪郭の量」で見せ場を点数化する。**輪郭で測るのが要点**で、
   これをやらないと振り回しただけのブレたカットばかり拾ってしまう
3. プランJSONの区間（曲の構造に合わせた尺）にカットを割り当てる
4. 区間ごとにイージング付きの寄り・スロー・色味を掛けて書き出す
5. つないで、テロップを重ねて、曲を乗せる

出力と一緒に `*_edl.json`（カット表）も出るので、AviUtl で詰め直すときの下敷きになる。

### 素材の区間分け

映像の中身までは判別できない。**素材フォルダに `01_歩き/` `02_準備/` `03_プレー/`
`04_衝突/` のようなサブフォルダを作るのが一番確実。** 無い場合は動きの量で自動的に
振り分けるが、「歩いている絵」と「表情の絵」の区別まではつかない。

### 色味は素材を測ってから決める

一律の数値を掛けると必ず失敗する。真昼の順光と夕方では出発点がまるで違うからだ。
このスクリプトは素材の黒・中間・白を先に測り、目標値へ寄せる曲線を組み立てる。
彩度は階調カーブの副作用で上がるので、1.5秒だけ試し焼きして係数を割り出している。

### プランJSONの作り方

`scripts/prime_plan.json` が楽曲『Prime』用の実例。別の曲に差し替えるときは、
`analyze_reference.py` で曲の音量の推移を出し、**音が落ちる区間をブレイクに、
立ち上がる位置を区間の境目に**割り当てる。区間ごとに指定できるのは
カットの長さの範囲・再生速度・寄りの量・イージングのカーブ・連射の位置。

### 限界

- **フレームレートを超えるスローは作れない。** 30fps素材で速度0.6にすると
  実質18fpsになりカクつく。素材が30fpsなら、スローは0.85程度までに留める
- 何が写っているか（顔なのか、スクラムなのか）は判別できない。フォルダ分けで補う
- あくまでたたき台。カットの入れ替えと締めの詰めは人がやる

## 7. シルエット素材を作る（ペルソナ5風など）

人物だけを黒単色にして背景をグリーンバックにした素材は、
「シルエット → シーンチェンジ → 実写」という見せ方の要になる。
`scripts/make_silhouette.py` がこれを作る。

```bash
pip install av ai-edge-litert scipy pillow numpy imageio-ffmpeg
# モデルを取得（初回のみ）
mkdir -p models
curl -L -o models/deeplab_v3.tflite \
  https://storage.googleapis.com/mediapipe-models/image_segmenter/deeplab_v3/float32/1/deeplab_v3.tflite
curl -L -o models/selfie_multiclass_256x256.tflite \
  https://storage.googleapis.com/mediapipe-models/image_segmenter/selfie_multiclass_256x256/float32/latest/selfie_multiclass_256x256.tflite

python scripts/make_silhouette.py 素材.mp4 -o silhouette_green.mp4
```

### クロマキーや輝度キーでは絶対にうまくいかない

芝・空・白線・フェンスを必ず拾ってノイズだらけになる。人物セグメンテーションの
モデルを使うこと。これは選択ではなく前提。

### 効いている工夫

1. **2段構え。** deeplab_v3 で全画面から人物の位置を掴み、そこを切り出して
   selfie_multiclass に入れ直す。256x256 の入力を1人ぶんに使うので、
   全画面で回すより腕・脚の隙間がはっきり出る（実測で別物になる）
2. **切り出す前に箱を統合する。** 1人が「頭」「胴」「脚」に分裂して検出されるのは
   日常茶飯事で、分裂したまま切り出すとシルエットがバラバラになる。
   `--merge` で膨らませてから連結成分を取り、1人1箱にまとめる
3. **切り出しの余白は狭く（`--pad 0.08`）。** このモデルは人物が画面いっぱいに
   写っている前提で学習されているので、余白が広いと精度が落ちる。
   実測で pad 0.30 → 0.08 にすると、画面端で見切れた人物の分断が解消した
4. **人らしくない形を捨てる。** 極端に横長（`--max-aspect`）・小さすぎる
   （`--min-area` `--min-height`）連結成分は、白線やフェンスの誤検出。
   これを落とすのがノイズ対策の本体
5. **輪郭はぼかしてから閾値を取り直す。** ギザギザだけ取れて形は保たれる
6. **時間方向は平均ではなく中央値（`--temporal`）。** ここは間違えやすい。
   前後フレームの**平均**を取ると、動いている手足の位置が混ざって輪郭が太り、
   脚の隙間が埋まり、伸ばした腕が消える。実際にそれで人の形が崩れた。
   **中央値**なら1フレームだけのチラつきは消えて、形はそのまま残る。窓は±1で足りる
7. **モルフォロジーの「閉じる」は使わない。** `binary_closing` は隙間を埋める処理なので、
   脚と脚の間・腕と胴の間を癒着させて人の形を壊す。穴埋めは `binary_fill_holes` で
   足りているので、突起を削る「開く」だけにする
8. **輪郭の平滑化を強くしすぎない。** 強いと脚の間の細い隙間が潰れる。1.2程度
9. **小片除去は形を整えた「あと」にもう一度掛ける。** 平滑化とモルフォロジーは
   成分を削るので、そこで新しい小片が生まれる。フィルタを前半だけに掛けていると
   取りこぼしがそのまま残る（実測で32.5%のフレームに小片が残っていた）

### 速度

`--merge` の膨張を原寸で掛けると1フレーム2秒以上かかる。縮小してから掛ければ
結果はほぼ同じで100倍速い。箱を決めるだけの用途なので精度はこれで足りる。

### 確認の仕方

`--preview 0.5,6.0,12.0` で指定秒のPNGだけ出せる。**必ず原画と並べて目で見ること。**
面積の数値だけ見ていても、分断や誤検出には気づけない。

## 8. 公開前に必ず確認すること

学校やチームの動画では、出来より先にここを片づける。飛ばさないこと。

- **BGM の著作権** — 市販曲をそのまま使ってネット公開すると、ブロックされるか収益が権利者に行く。

## 参照ファイル

必要になったときに読む。最初から全部読む必要はない。

- `references/aviutl.md` — AviUtl とプラグインの導入、スクリプトの設置、色味・黒帯・書き出しの具体的な操作、うまくいかないときの対処
- `references/shooting.md` — 撮影設定、撮るべきカットの一覧、やりがちな失敗
- `references/telop.md` — テロップと文字演出の型、字体の選び方、情報の組み方
- `scripts/make_silhouette.py` — 人物を黒・背景をグリーンバックにしたシルエット素材を作る
- `scripts/prime_plan.json` — 楽曲『Prime』に合わせた編集プランの実例（区間・色味・テロップ）

## 成果物の渡し方

作業が終わったら、変更したファイル・使い方・確認方法・注意点をまとめて伝える。
スクリプトを新しく書いた場合は、**AviUtl が読めるよう Shift-JIS + CRLF で保存する**
（UTF-8 で保存すると項目名が文字化けする）。Lua の挙動は、
`obj` を模したテーブルを用意すれば AviUtl なしでも検証できる。
