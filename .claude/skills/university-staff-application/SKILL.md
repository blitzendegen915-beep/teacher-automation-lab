# 大学職員 応募書類の作成

高校英語科教員（私立中高一貫・大学附属校・約7年）の経歴を、大学職員の採用基準に接続した応募書類を作る。

## この仕事の要件（依頼者が明示した4点）

1. **経歴を大学職員に接続する** — 教員の言葉のままでは伝わらない。職員の業務語彙に翻訳する
2. **盛らない** — 事実にない実績・数字を足さない。面接で崩れる書き方をしない
3. **熱意が採用側に伝わる** — 抽象的な意欲表明ではなく、事実と具体策で示す
4. **文字数を確保する** — 与えられた枠を使い切る。短い提出は「書くことがない人」と読まれる

この4点は同時に満たす。どれか一つを犠牲にした原稿は不合格とする。

## 進め方

1. 求人票（または大学名・URL）を受け取る。**マイナビ等の求人サイトは自動取得が403で弾かれる**。依頼者に本文を貼ってもらうのが早い
2. **求人票から次を必ず抽出する**。ここを飛ばして書き始めない
   - **応募完了の条件**（フォーム送信だけか、職務経歴書PDFの別途提出が必要か）
   - **設問ごとの字数指示の有無**（後述。事故が最も多い）
   - 雇用形態（正職員か有期か）／応募資格の必須・歓迎／求める人物像
   - 中期計画・将来構想の**名称と柱**／募集背景／業務領域の一覧／設置校の構成
   - 選考フローと日程／転勤範囲／入職時期
3. 抽出結果を提示し、依頼者の実績のどれを当てるかを決める
4. 初稿を書く
5. **人事目線で採点する**（後述）。90点未満なら書き直す
6. 文字数を実測し、コピペできる形で出す

## 文字数の判断（最も事故が多い）

**必ずこの順で判断する。**

1. **求人票に字数指示があるか** → あればそれが絶対。フォームの入力上限より優先する
   - 実例：フォーム上限800字でも、求人票に「入力可能文字数に関わらず400文字以内」とあれば400字。事務職の採用で指示遵守は評価項目そのもの
   - この場合は**上限の96〜99%**を狙う（400字なら385〜398字）
2. **指示がない場合** → フォームの上限が事実上の期待値。**上限の85〜92%**を狙う
   - 800字なら680〜740字。上限ちょうどは避ける（フォームの判定差で弾かれる）
3. **伸ばすときは情報を足す。水増ししない**
   - 足していいもの：課題→打ち手→結果の欠けている段、歓迎分野への直接接続、求める人物像のうち未カバーの要素、勤務条件の受諾表明
   - 足してはいけないもの：言い換えの反復、求人票の引き写し、「貢献したい」だけの文

日本語の文字数は必ず **Python の `len()` で実測する**。目視やモデルの自己申告は当てにならない。

## 応募先ごとの作り分け

- **自己PRは応募先非依存に作る**。一度完成させれば全大学で使い回せる
- **差し替えるのは志望動機だけ**。ここに応募先固有の情報を集中させる
- 応募先の字数枠が広い場合のみ、自己PRに歓迎分野への接続を追記する

## 経歴の翻訳（教員の言葉 → 職員の言葉）

| 実務経験 | 大学職員の言葉 | 当てる部署 |
| --- | --- | --- |
| 英検準会場の運営責任者 | 試験実施の全体設計・運営責任。申込集約、名簿・座席・監督者配置、機密書類管理 | 入試・教務 |
| 校務DX（GAS/VBA/生成AI） | 業務プロセスの標準化と自動化。属人化の解消 | 情報システム・DX推進・企画 |
| 担任・学級経営 | 個別事情の把握、記録、関係部署との連携、一次対応 | 学生支援 |
| 進路指導 | キャリア支援。出願管理、締切管理、志望理由の言語化支援 | キャリアセンター・入試広報 |
| 学校説明会・私学展 | 対外広報とステークホルダー対応 | 広報・入試広報 |
| 職員会議資料 | 会議体の運営と文書管理 | 総務・法人事務局 |
| 学校行事の運営 | 多部門横断のプロジェクト運営、予算・安全管理 | 総務・学生支援 |
| 部活動顧問 | 課外活動の統括と渉外、安全配慮義務 | 学生支援 |
| 英検1級・大学院修了 | 実務レベルの英語運用能力＋学術的訓練。教員組織と話が通じる | 国際・研究支援・教務 |
| **大学附属校での勤務** | **学校法人の意思決定構造を内側から理解。高大接続・系列校連携・内部進学** | 教務・企画・高大接続 |

最後の行が最大の差別化要因。**他の中途応募者が体験として語れない**。志望動機に必ず入れる。
応募先が附属校・系列校を持つ法人なら、その構成に名指しで触れる。

詳細と面接用エピソードは `docs/university_staff/` を参照する。

## 生成AI・AIコーディングエージェントの扱い

DX推進や情報システムを歓迎する求人では強い武器になるが、**書き方を誤ると減点される**。

- **書類にツール名（Claude Code、Codex等）を出さない**。知らない読み手にはノイズ、知っている読み手には「本人のスキルはどこまでか」という疑問を生む
- 「バイブコーディング」等の語は業務文書では使わない
- **成果と運用ルールで書く**。例：「生成AIについても、入力してよい情報の範囲を定めた上で、教材作成と校務の実務に組み込んで運用しております」
- 職務経歴書の**スキル欄でのみ**、一般名詞で書いてよい。例：「生成AIを用いた開発支援ツール（AIコーディングエージェント）を業務改善に活用し、校務ツールおよびWebサイトの設計から公開・運用までを内製」
- **面接では出す**。ただし必ず「AIが書いたものをそのまま使わない」「動作確認・手順書・入力してよい情報の線引きは人間の責任」を添える。ここで「AI頼みの人」と「AIを管理できる人」に分かれる
- **GitHubリポジトリのURLは渡さない**。転職活動用の資料やブランチ名が見える。見せるなら公開済みのGitHub Pages等、成果物のURLだけ

## 盛らないための規則

- 事実リストにない実績・数字を書かない
- 数字は「約」「程度」「延べ」を付けて幅を持たせる。断言して後で崩れる損失のほうが大きい
- 正確な数字が出せない項目は、その語ごと削る。曖昧な数字を置かない
- **現在も継続している業務は現在形**（「維持しております」）。過去形にすると退職済みか中断したと読まれる
- **勤務条件の受諾表明（転勤可、夜間勤務可など）は、本人が実際に受け入れられる場合のみ書く**。書いた以上、面接で撤回できない。迷いがあるなら書かせず、その旨を依頼者に確認する

## 熱意の出し方（抽象表現を使わずに）

- 「貢献したい」「成長したい」だけの文を書かない。必ず事実か具体策とセットにする
- **入職後に何をするかを1〜2文入れる**。応募先固有の課題に対する具体策であること
- 応募先固有の固有名詞を**2つ以上**入れる（建学の理念、中期計画名とその柱、募集背景、設置校構成、求人票が使っている特徴的な言い回し）
- **求人票の言葉を引用して応答する**。「裏方に徹するという旧来の考え方にとらわれず」のような相手自身の表現を拾うと、読み込んだ応募者だと伝わる
- **失敗とその突破を1つ入れる**。成功だけ並べた自己PRは全員が書く。失敗を書ける応募者は現場を回した人間だと判定される
- 求める人物像が列挙されている場合、**言葉をそのまま借りずに**対応要素を織り込む

## 文章の規則

- 一人称は「私」。文末は「〜です」「〜ます」「〜ております」。「〜と思います」は使わない
- 同じ文末表現を3回以上連続させない
- 応募先は「貴学」。学校法人に応募する場合は「貴学院」等、相手の自称に合わせる。正式名称を使う
- **「生徒」と書かない。「学生」**。ただし自分の過去の職務を述べる文脈では「生徒」で正しい
- 一文は60字以内を目安
- 提出前に、他大学の名前が混入していないか検索する（使い回し最大の事故）

## 職務経歴書（PDF提出が求められる場合）

- **応募先が書式や記載方法を指示していれば、それが最優先**。例：「年代は必ず西暦」「同一会社内の異動・転出も記入」
- 同一法人内の分掌異動は、**年次の表**にして変遷が追える形にする。多くの応募者が箇条書きで済ませる欄なので差がつく
- 実績は**課題→対応→結果**の3段で書く。3〜4本
- A4で2〜3枚。PDFに変換して提出
- **フォーム送信だけで応募完了と思い込まない**。別途アップロードが必要な場合、出し忘れると書いた文章が全部無駄になる

## 選択式の設問

- **「即戦力として働ける業務」は2つに絞る**。3つ以上選ぶと、字数制限のある付随設問で1件あたりが薄くなる。「即戦力」と言い切れる裏づけがあるものだけ選ぶ
- **入社希望日は、年度末までの在職を前提に選ぶ**。教員が年度途中で抜ける選択肢を選ぶと、無責任と読まれるリスクが、早期着任のアピールを上回る

## 採点（90点未満は出さない）

| 観点 | 配点 | 不合格の例 |
| --- | --- | --- |
| 経歴が職員業務に接続されているか | 25 | 教科指導の話で終わっている |
| 応募先固有性 | 20 | 固有名詞が2つ未満。どの大学にも出せる |
| 具体性（事実・数字・打ち手） | 20 | 「調整力があります」など根拠のない主張 |
| 字数の使い切り | 15 | 枠に対して不足。または指示を超過 |
| 事実の正確さ | 10 | 盛り、時制の誤り |
| 日本語（文末・語彙・敬語） | 10 | 文末の連続、「生徒」の混入 |

減点が集中しやすいのは**字数と固有性**。この2つを先に確認する。
満点にならない理由が経歴側（大学職員としての実務未経験）にある場合は、そう明言する。文章では埋まらない。

## 分担とトークン運用

- **オーケストレーター（Opus）**: 求人票の読解、実績の選定、人事目線の採点、事実確認、文字数の実測、確定版の作成
- **文章出力係（Sonnet）**: 初稿の作成。制約（字数範囲・使う実績・構成・禁止事項）を渡して書かせる
- Sonnet に渡すプロンプトには、**応募者の事実リストを列挙し「これ以外を創作しない」と明記する**。事実リストを渡さないと必ず盛る
- ただし**すでに文脈を保持していて短い改稿で足りる場合は、委譲せず自分で書く**。委譲は数万トークンかかるため、往復のほうが高くつくことがある
- 求人票の全文を再投下せず、抽出済みの要点だけを回す。確定したテキストは会話に再掲しない

## 完了時に報告すること

1. 求人票から抽出した要点（応募完了の条件・雇用形態・字数指示・選考日程・転勤範囲）
2. 各設問の確定テキストと**実測文字数**（上限に対する割合も添える）
3. 採点結果と、満点にならなかった理由
4. 選択式設問の推奨と根拠
5. 提出前チェック（字数・固有名詞・他大学名の混入・時制・別途提出物の有無）
